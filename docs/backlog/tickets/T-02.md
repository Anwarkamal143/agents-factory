## Context
The thinnest complete path through every layer: CLI -> config -> engine -> state machine -> adapter -> engine-run verification -> event log -> status. Everything later deepens a layer of this path. Read SPEC-01 (`docs/spec/SPEC.md`): "Task state machine", "Event log and store", "Contracts", "Verification". Workspace is a plain temp directory for now; git worktrees arrive in T-10. Review and integration stages are not implemented yet, so this ticket uses a **dev-only `minimal` workflow** that goes `running -> verifying -> succeeded`; that workflow must be marked `dev_only` and refused for delivery (the full invariant in the spec applies to the default workflow from T-11/T-10 onward).

## What to build
- `factory run --adapter fake --project <dir> "<request text>"`: creates a run, one task (objective = request text), executes it via the fake adapter, runs the project's `verify` commands **itself**, records events, exits.
- `factory status <run>` and `factory events <run>`.
- Fake adapter driven by a scenario file inside the project fixture (`scenario.json`): `ok`, `verify_fails` (agent claims success but the file is wrong), `invalid_output`.
- JSON Schemas with good/bad fixtures: `event`, `task-input`, `task-result`, `verification-result`, `project-config` (minimal).
- Run ids and timestamps come from an injected clock and id source so tests are deterministic.

## Demo path
```
$ factory run --adapter fake --project fixtures/hello "create hello.txt containing hi"
run R-0001 completed (1/1 tasks succeeded)          # exit 0
$ factory events R-0001
1 run.created            2 task.created           3 task.transitioned pending->ready
4 task.transitioned ready->running   5 attempt.started   6 attempt.finished(status=succeeded)
7 task.transitioned running->verifying   8 verification.recorded(passed=true)
9 task.transitioned verifying->succeeded   10 run.transitioned executing->completed
```
(Event 1 may include `created->executing` as event 2 if you model it; keep the sequence in the test literal and the CLI consistent.)

## Acceptance criteria
- [ ] The demo command exits 0 and `events` lists exactly the sequence above (asserted as a literal list of `(type, from, to)`), with `seq` gapless from 1 and each `crc32` equal to the CRC32 of the canonical JSON of the other fields.
- [ ] Scenario `verify_fails`: exit code 1, task ends `failed`, run ends `failed`, the last verification event has `passed=false` and a non-zero `exit_code`; the agent's claim of success appears in `attempt.finished` but does **not** make the task succeed.
- [ ] Scenario `invalid_output`: the adapter returns text that does not validate against `task-result`; task ends `failed` with an `attempt.finished` event whose `status` is `invalid`; no verification is run.
- [ ] `verify` given as a string (not an argv array) in `project.yaml` is rejected before any run starts: exit code 2 and a message naming the offending key.
- [ ] Deleting `snapshot.json` and running `factory status <run>` prints identical output (state rebuilt from the log).
- [ ] Every emitted event validates against `event.schema.json`; each bad fixture (missing `seq`, wrong `type` enum, bad `crc32`) is rejected by the schema tests.

## Seams
Primary: **Engine API / CLI** (black box over a fixture project and a scripted fake adapter). Secondary: **Schemas** (fixtures only). The adapter operations used (`start`, `result`) are exercised through the engine, not directly; the full adapter contract suite arrives in T-12.

## TDD plan
Work as vertical red-green slices, one test at a time, confirming each fails for the right reason first. Expected values are literals, not recomputed with the production code. Compute the literal CRC32 for the fixed payload once with an independent tool and paste it.
1. Event writer: append 3 events with a fixed clock -> file has 3 lines, `seq` 1,2,3, `v` 1, literal `crc32` values.
2. State machine, table-driven: legal pairs (`pending->ready`, `ready->running`, `running->verifying`, `verifying->succeeded`, `verifying->failed`) accepted; illegal pairs (`pending->running`, `succeeded->running`) raise a `TransitionError` naming both states.
3. `ok` scenario end to end: assert the 10-event literal sequence and exit 0.
4. `verify_fails` scenario: assert states, exit 1, `passed=false`.
5. `invalid_output` scenario.
6. Config: string `verify` rejected with exit 2.
7. Replay: remove snapshot, `status` output equal.
8. Schema fixtures good/bad.
Do not mock internal modules; the fake adapter is the only test double and it implements the real adapter interface. Mocks only for clock, id source, and subprocess *timeouts*.

## Implementation notes
- Modules (names, per SPEC "Module map"): `contracts`, `core.config`, `core.events`, `core.store` (simple append + `fsync` + snapshot-from-log for now; hardening in T-03), `core.statemachine`, `core.verify`, `core.workflow` (only `minimal`), `adapters.fake`, `cli`.
- State dir: `.factory/state/<run>/{events.jsonl, snapshot.json, artifacts/}` inside the **project** directory.
- Canonical JSON for `crc32`: sorted keys, separators `(',', ':')`, UTF-8, excluding the `crc32` field itself.
- Verification runner: argv arrays only, `cwd` = task workspace, environment allow-list (`PATH`, `LANG`, `CI`), default timeout 300 s, stdout/stderr saved under `artifacts/` with sha256 recorded in `artifact.recorded`.
- Exit codes: 0 completed; 1 failed/blocked; 2 usage or config error. Anything else is a bug.
- Public functions have docstrings stating contract; no global state; no network; no git.
- Use the GLOSSARY nouns for names (Run, Task, Attempt, Verification, Event).

## Security & failure notes
Never run verification through a shell. Never write outside `.factory/state/<run>/` and the task workspace. Redact environment values from all logs. A crash between writing an event and updating the snapshot must be recoverable by replay (the snapshot is derived, never authoritative). Disk-full on append must fail the run loudly (non-zero exit), never silently drop events.
