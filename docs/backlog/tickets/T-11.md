## Context
The predecessor's reviewer was an LLM lane whose verdicts were prose. Here review is a stage with a typed result, independence rules, and a convergence cap, so a loop cannot run forever. Read SPEC-01 "Task state machine" (`reviewing` rows) and "Contracts" (`findings`).

## What to build
- After engine-run verification passes, run the **reviewer role** in a **separate adapter session** whose `task-input` contains: the diff against base, the spec acceptance items for the task, and the project standards text. It must **not** contain the builder's `summary`, `questions` or reasoning (independence).
- **Finding schema:** `{id, severity: blocker|major|minor|nit, axis: standards|spec|security, location, text, citation}`; `citation` is a standards rule id, a smell name with the hunk, or an acceptance id (`AC-n`). A finding without a citation is **invalid** and dropped with an event (`finding.rejected`, reason `uncited`).
- **Rule:** any `blocker` or `major` => `reviewing -> running` with the findings as context (counts an attempt); `minor`/`nit` are recorded only. No finding at all => `reviewing -> integrating`.
- **Convergence cap:** `max_review_rounds` (default 2). After the cap with blocking findings still open => task `blocked`, reason `review_not_converging`. Round 2+ gives the reviewer only changed hunks plus the previous findings and their status.
- **Per-axis report:** the stored review result lists the worst finding **per axis** and never merges axes into one score.
- Fake reviewer scenarios: `clean`, `blocking_then_clean`, `always_blocking`, `uncited_finding`, `minor_only`.

## Acceptance criteria
- [ ] `clean`: the task passes `reviewing -> integrating` with zero findings.
- [ ] `blocking_then_clean`: first review has one `blocker` citing `AC-1` => back to `running`; the second review is clean; two review sessions exist, each a distinct adapter handle.
- [ ] `always_blocking` with cap 2: task `blocked` reason `review_not_converging` after exactly 2 rounds.
- [ ] `uncited_finding`: the uncited finding is rejected (`finding.rejected` event) and does **not** block the task.
- [ ] `minor_only`: findings recorded, task proceeds.
- [ ] The reviewer's `task-input` contains no `summary` or `questions` from the builder (schema-level assertion on the captured input).
- [ ] The stored review result has a `worst_per_axis` object with keys `standards`, `spec`, `security` (null when none) and no combined score field.

## Implementation notes
- Reviewer prompt assets live as Markdown under `components/agents/reviewer.md` (no control flow in prose); the engine owns rounds and routing.
- Do **not** run the review in a loop until it comes back clean; the cap is the rule (a known failure mode of AI review is endless new findings each round).
- Waiving a finding is a human action (post-MVP); do not add an agent-waivable path.

## Out of scope
Review prompt tuning, adversarial multi-agent review, auto-fixing findings beyond routing back to the builder.

## Decisions & questions
None blocking.

## Security & failure notes
Reviewer is read-only (permission profile: no writes except its result artifact, no network, no shell). Findings text is untrusted output: never interpreted as instructions by the engine; truncated to a bounded length.

## Definition of done
