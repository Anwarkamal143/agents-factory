## Context
Turns an approved spec into a validated task graph. The predecessor judged overlap and sizing by LLM at run time; here the plan is a typed artifact the scheduler and the human can inspect before any code is written. Read T-05 (plan schema) and T-07 (write sets), SPEC-01 "Scheduler".

## What to build
- **Planner role** (read-mostly profile) returns `plan.json` in the T-05 schema.
- **Validators (engine-side):** acyclic; ids unique; every acceptance id (`AC-n`) from the approved spec is covered by >= 1 task (`acceptance_ids`); every task has a non-empty `write_set` unless it carries explicit `write_set_unknown: true` (then it is flagged and serialized against everything); size limits (objective <= 2000 chars, tasks <= 50 by default); predicted `risk_classes` per task (advisory, shown at approval).
- **Overlap report:** the pairs of tasks that will be serialized because their write sets overlap (from T-07's predicate).
- **`factory plan show <run>`:** a table plus a Mermaid `flowchart TD` of dependencies.
- **Approval:** `plan.approve` per the matrix; pinned to plan hash; editing the plan file after the request invalidates it. Reject with a note => planner re-runs with the note as context (plan version `P-<run>-<v>` increments).
- Fake scenarios: `plan_ok`, `plan_uncovered_ac`, `plan_cycle`, `plan_overlap`, `plan_unknown_write_set`.

## Demo path
```
$ factory plan show <run>
T-1 add divide        deps: -      write: calc.py         risk: -
T-2 fix mean([])      deps: -      write: calc.py         risk: -      (serialized after T-1: write-set overlap)
flowchart TD ...
$ factory approve AP-0002          # plan approval
state: executing
```

## Acceptance criteria
- [ ] `plan_uncovered_ac` (spec has AC-1..AC-3, plan covers AC-1 and AC-3): invalid, the message lists `AC-2` literally; repair-once then failure.
- [ ] `plan_cycle`: rejected with the cycle path in the message.
- [ ] `plan_overlap`: the overlap report lists the exact task-id pair and the shared pattern.
- [ ] `plan_unknown_write_set`: accepted only with `write_set_unknown: true`; the plan view flags it and the scheduler serializes it.
- [ ] `plan show` output contains the line `flowchart TD` and one node per task id (literal check).
- [ ] Editing the plan after the approval request invalidates the approval; rejecting with a note produces `P-<run>-2` whose planner input contains the note.
- [ ] More than 50 tasks (configurable limit) is rejected before approval with the limit named.

## Implementation notes
- Reuse the T-05 loader; add coverage and limit rules as small named validators.
- Mermaid is plain text output; do not depend on a renderer.
- Keep the planner prompt asset in `components/agents/planner.md`; no routing logic in prose.

## Out of scope
Automatic plan repair beyond repair-once; effort estimation; re-planning mid-execution (a failed task blocks, it does not rewrite the plan; post-MVP).

## Decisions & questions
None blocking.

## Security & failure notes
Planner output is untrusted: size, depth and count limits; never use plan strings as paths without normalization and a check that resolved paths stay inside the repo (write sets with `..` or absolute paths are rejected).

## Definition of done
Criteria checked; example plan in `docs/examples/`; GLOSSARY updated (Acceptance coverage, Overlap report); PR includes the validator list.
