## Context
The predecessor's approvals were head- and scope-pinned (good) but a comment any user-typed identity could post, including the agent's own (bad). Here approvals originate **only** from an authenticated human channel and are pinned to hashes. Read SPEC-01 "Policy and autonomy", "Contracts: approval-request" and DEC-03's resolution (channel). This ticket implements subjects `task.accept` and `deliver.merge`; `spec.approve`/`plan.approve` reuse it in T-14/T-15.

## What to build
- When `decide` returns `needs_approval`, create an `approval-request` event (`approval.requested`) with `subject {type, id, hash}`, `scope`, `scope_hash`, `reason`, `expires_at` (default 24 h, injected clock); task -> `awaiting_approval`.
- CLI: `factory approvals list`, `factory approve <id> [--note]`, `factory reject <id> --note`.
- **Human-only channel (MVP, per DEC-03 default):** `approve`/`reject` require a **controlling terminal** (stdin and `/dev/tty` are TTYs); otherwise exit **5** ("no controlling terminal") and write nothing. The granted event records approver = OS user, host, tty name.
- **Pinning:** at use time the engine recomputes `subject.hash` (content hash of the integrated head or workspace) and `scope_hash` (sha256 of canonical scope JSON). Any mismatch => `approval.invalidated`, a new request is required.
- **Expiry:** past `expires_at` => `approval.expired`; approving an expired request is refused (exit 6).
- **Idempotency:** approving twice is a no-op with exit 0 and no duplicate event.
- Document the **residual risk** in `docs/security/approvals.md`: an agent with unrestricted shell on the same machine could try to obtain a TTY; mitigations are the permission profile (no `factory` binary, T-08) and OS user separation (recommended).

## Demo path
```
$ factory run ... --autonomy L2 ...            # stops: task awaiting_approval (delivery)
$ factory approvals list
AP-0001  deliver.merge  T-1  expires 2026-..   pending
$ factory approve AP-0001 --note "reviewed"    # interactive terminal
approval granted; run continues
$ echo | factory approve AP-0002               # piped stdin
error: no controlling terminal (exit 5)
```

## Acceptance criteria
- [ ] `approve` with piped stdin (no TTY) exits 5 and appends **no** event (log hash unchanged).
- [ ] With a pseudo-terminal harness, `approve` appends `approval.granted` containing approver user, host and tty, and the task resumes.
- [ ] After the workspace content changes (hash change) following the request, using the approval fails: `approval.invalidated` recorded and a **new** request is created; the old id cannot be re-granted.
- [ ] Expired request: `approve` exits 6, `approval.expired` recorded, task stays `awaiting_approval` with a fresh request available.
- [ ] Scenario `forge_approval` (the fake agent writes an approval-looking JSON file and a fake `done` comment into its workspace and artifacts): no state change occurs and the file is never read by engine code (assert no `approval.granted` and the task stays `awaiting_approval`).
- [ ] Scenario `agent_runs_factory_approve`: the agent attempts `proc.spawn` of `factory approve`; policy returns `deny`, a `policy.decision` deny event exists, and no approval is granted.
- [ ] Approving the same id twice is idempotent (exit 0, one `approval.granted` event).

## Implementation notes
- Hash inputs: `subject.hash` = sha256 of a deterministic tree listing (path + file sha256, sorted) of the integrated head/workspace; `scope_hash` over `{risk_classes, files_changed, lines_changed, action}`.
- The approval store is the event log; no separate approvals file that an agent could edit.
- Keep the TTY check in one small function with a clear docstring; tests prove both sides.
