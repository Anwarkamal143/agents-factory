## Context
The analyzed predecessor documented retry caps and a "no progress" halt only in prose, and its code never enforced them. Here they are engine code. Read SPEC-01 "Task state machine" (attempt rows, root-cause cap) and "Contracts" (`budgets`, `usage`).

## What to build
- **Attempt cap:** `max_attempts` (default 3). Verification failure with attempts left: `verifying -> running` passing the failure log as context. Exhausted: task `failed`, run `blocked`.
- **Failure signature:** sha256 of `check name + exit code + last 20 lines of combined output` after normalizing digits, timestamps and absolute paths. **Same signature twice in a row => task `blocked`** with reason `repeated_failure` (before exhausting the cap).
- **No-progress:** two consecutive attempts whose workspace content hash is identical and which still fail => `blocked` with reason `no_progress`.
- **Wall-time budget** per attempt (`budgets.wall_s`): on expiry call adapter `cancel(handle, grace_s)`, then kill the process group; emit `attempt.interrupted` with reason `timeout`; the attempt counts.
- **Run token budget:** sum `usage.tokens_in + tokens_out` from results; exceeding it emits `budget.exhausted` and makes the run `blocked` (running attempts are cancelled first).
- **Repair-once:** an invalid `task-result` triggers exactly one repair request with the schema error; still invalid => attempt fails.
- **`factory cancel <run>`:** writes a `cancel.request` file in the run's state dir (the engine is the only event writer); the engine notices within 1 s (poll with the injected clock), cancels adapters, marks non-terminal tasks `canceled`, run `canceled`, keeps workspaces.
- New fake-adapter scenarios: `flaky_then_success`, `always_fails_same_way`, `fails_differently_each_time`, `slow`, `token_hog`, `makes_no_change`.

## Demo path
```
$ factory run --adapter fake --project fixtures/always_fails_same_way "x"
task T-1 blocked: repeated_failure (2 attempts)        # exit 1
$ factory run --adapter fake --project fixtures/flaky_then_success "x"
run completed (1/1 tasks succeeded, attempts: 2)       # exit 0
```

## Acceptance criteria
- [ ] `flaky_then_success`: final `succeeded`, exactly two `attempt.started` events, the second attempt's task-input context contains the first failure log.
- [ ] `always_fails_same_way` (cap 3): task `blocked` with reason `repeated_failure` after **2** attempts, not 3.
- [ ] `fails_differently_each_time` (cap 3): task `failed` after 3 attempts, run `blocked`, exit 1.
- [ ] `slow` with `wall_s=1`: `attempt.interrupted` reason `timeout`; the child process and its children no longer exist afterwards (test checks the pid).
- [ ] `token_hog` with a run budget of 1000 tokens: `budget.exhausted` is recorded and the run ends `blocked`; no new attempts start afterwards.
- [ ] `makes_no_change` failing twice => `blocked` with reason `no_progress`.
- [ ] `factory cancel <run>` during a `slow` attempt: the run ends `canceled`, no child process remains, the `factory run` process exits **130**, and `factory cancel` itself exits **0** when the request was accepted (**1** for an unknown run id).
- [ ] An invalid result is repaired once when the fake adapter's second response is valid; when still invalid the attempt fails (two assertions).

## Seams
**Engine API/CLI** primarily (black box over scenarios). **Adapter contract** only through `cancel` behaviour.

8. Repair-once both branches.
9. Cancel.

## Implementation notes
- Defaults live in config (`budgets`, `max_attempts`); per-task override from the plan later.
- Use the injected clock for all deadlines; never `sleep` in tests (the fake adapter blocks on an event the test controls).
- Process-group kill must handle children started by the verification runner too.
- Record every limit hit as an event with the numeric limit and observed value.

## Out of scope
Dependency propagation (T-05), parallelism (T-07), approvals, real adapter timeouts (T-13 maps them).

## Decisions & questions
None blocking. Flag if the signature normalization rules look wrong for a real project's output (follow-up issue).

## Security & failure notes
Never leave orphan processes; kill by process group; verify with a test. A failure log passed back to the agent is untrusted data from the engine's point of view and is truncated (default 8 KB) to bound context.
