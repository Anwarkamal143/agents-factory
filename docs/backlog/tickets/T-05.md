## Context
Until now a run has one task. This ticket introduces a plan of several tasks with `depends_on` edges, run sequentially. The plan stage that *generates* plans comes in T-14/T-15; here the plan is a hand-written `plan.json` validated by schema. Read SPEC-01 "Scheduler" and the task state table (`pending -> ready`, `blocked`).

## What to build
- `factory run --plan plan.json --adapter fake --project <dir>`.
- Plan schema + validators: unique task ids, known dependency ids, **acyclic** (report the cycle path), non-empty objective, `write_set` list present (may be empty), `acceptance_ids` list.
- Scheduler (sequential): a task is `ready` when all `depends_on` are `succeeded`. Pick the oldest ready task first (plan order).
- **Failure propagation:** if a dependency ends `failed`, `blocked` or `canceled`, every transitive dependent becomes `blocked` with reason `dependency:<id>` (not `failed`, and not executed). Independent branches still run.
- Run result: all tasks `succeeded` -> `completed`; otherwise `blocked`.
- Fail-safe: a dependency id that disappears or cannot be read at runtime makes the task not ready (never "assume satisfied").

## Demo path
```
$ factory run --plan fixtures/chain.json --adapter fake --project fixtures/chain
run completed (3/3 tasks succeeded)
$ factory events <run> | grep "ready->running"     # tasks start in order A, B, C
```

## Acceptance criteria
- [ ] Chain `A <- B <- C` starts tasks in order A, B, C (asserted as a literal ordered list of task ids from `attempt.started` events).
- [ ] Diamond `A <- B, A <- C, B <- D, C <- D`: D starts only after both B and C succeeded; B before C (plan order).
- [ ] Cycle `A <- B <- A` is rejected before any run: exit 2, message contains the literal path `A -> B -> A`.
- [ ] If B fails (scenario `verify_fails` for B only): C (depends on B) is `blocked` with reason `dependency:B` and never started; an independent task X still runs and succeeds; run ends `blocked`, exit 1.
- [ ] Unknown dependency id and duplicate task id each rejected with exit 2 and a message naming the id.
- [ ] No `attempt.started` event exists for a `blocked` task (negative assertion).

## Implementation notes
- Scheduler is a pure function `ready_tasks(task_states, depends_on) -> ordered ids`; the engine loop calls it. (Test it through the engine, not directly, unless it becomes a public seam.)
- Keep plan ordering stable and explicit (list order is the tiebreak).
- Emit `task.transitioned pending->blocked` with `reason` in the payload.
