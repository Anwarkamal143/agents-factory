## Context
Build this **only when a second component author exists** (a second person or project wants to add a skill or role). Until then, roles and skills are plain files and a registry is speculative generality. Read `docs/analysis/06-component-lifecycle-and-extensibility.md` (manifest, procedures).

## What to build
- `component.yaml` schema (`id, kind, version, contract, entry, requires{capabilities,components,tools}, permissions, triggers, inputs, outputs, supports, tests, deprecates`), generated registry `.factory/registry.json` (no hand-edited name lists).
- Commands: `factory component list|show|validate|add|disable|enable|swap|remove`.
- Rules: unique ids; dependency resolution with version ranges; capability compatibility checked against the active adapter's `capabilities.json`; `remove` refuses when dependents exist (unless `--cascade`); `swap` runs both components against golden fixtures and refuses unless contract tests pass; third-party components must declare `permissions` and **unpinned remote sources are rejected**; every change updates `factory.lock` (T-21).

## Demo path
```
$ factory component add ./my-skill     # validates manifest, deps, capabilities, updates lock
$ factory component remove tdd         # refused: required by builder@1
```

## Acceptance criteria
- [ ] A component with an unknown `kind`, missing `permissions` (third-party) or a dependency range with no match is rejected by `validate` with a message naming the field.
- [ ] `remove` of a depended-on component exits non-zero and lists dependents; `--cascade` removes dependents and records it in the lock.
- [ ] `swap` fails when the replacement violates the contract fixtures and leaves the old component installed (hash check).
- [ ] A skill requiring capability `subagents` is refused (or marked unavailable) with an adapter that lacks it; the message names the capability.
- [ ] A remote component reference without a pinned version/hash is rejected.
- [ ] `disable` makes a workflow that requires the component fail validation immediately (fail fast), and `enable` restores it.

## Implementation notes
- The registry is derived data and rebuilt from manifests plus the lock; never hand-edited.
- Keep skill and role assets as Markdown with a manifest beside them; no executable code in manifests.

## Out of scope
A marketplace or remote index; signing third-party components; sandboxing component code (components are prompt assets).

## Security & failure notes
A component can only **narrow** the permission profile, never widen it. Reject manifests that request `fs.write` outside the worktree or `net` for roles that do not need them.
