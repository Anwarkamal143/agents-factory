## Context
Wires every stage into the **default workflow** and proves the MVP. Until now the `minimal` dev-only workflow bypassed spec, plan, review and integration; the default workflow requires all of them. This ticket's acceptance **is** the MVP acceptance in SPEC-01 and in `docs/analysis/` (report 14, section "Minimum viable factory").

## What to build
- `workflows/default.yaml` (declarative; primitives `stage`, `for_each_task`, `loop(max, until)`, `gate(policy)`, `parallel(disjoint_write_sets)`), a workflow schema, and a loader that validates it. The `minimal` workflow stays `dev_only` and is refused for delivery.
- **Fixture repos** created by a setup helper (`py_calc`): task 1 feature (`divide`), task 2 bug (`mean([])`), tasks 3 and 4 both editing the same file (overlap pair).
- **Scripted fake agents** that perform real edits (patch files), so integration, conflicts and verification are real.
- **Scenario test:** `factory request` -> spec approve (pty) -> plan approve (pty) -> execute (parallel where disjoint, serialized where overlapping) -> review -> integrate -> delivery approve (pty) -> base branch updated.
- **Invariant checker** (reusable test helper, also used by T-18): for every task in every event log, `succeeded` implies engine-run verification passed on the integrated head, no open blocking finding, and every required approval granted.
- **Kill-and-resume inside the E2E:** `kill -9` during `executing`, then `factory resume`, same final result.
- One **`real`-tagged** run with the T-13 adapter on one fixture (manual/nightly) with the redacted transcript and event log committed under `docs/evidence/` as the MVP evidence.
- `docs/mvp-demo.md`: the run log excerpt and a Mermaid diagram of what happened.

## Demo path
```
$ pytest -m "not real" tests/e2e          # full lifecycle with the fake adapter, offline
$ factory request "..." --project fixtures/repos/py_calc --adapter <harness>   # the real run
$ git -C fixtures/repos/py_calc log --oneline          # commits with Task:/Run: trailers
```

## Acceptance criteria
- [ ] The offline E2E completes in default CI and ends with the base branch containing the expected commits (literal subjects) for all four tasks.
- [ ] The overlapping pair never runs concurrently (open-attempt invariant computed from the log); the disjoint pair does.
- [ ] The invariant checker passes on every event log produced by every E2E scenario in CI (and the checker is itself tested with a deliberately violating log that it rejects).
- [ ] Killing the engine with SIGKILL during `executing` and resuming yields the same final state and no duplicate `seq`.
- [ ] Attempting delivery without a granted approval (L2) never changes the base branch (negative scenario).
- [ ] The `minimal` workflow is refused for delivery with a clear message and exit code 2.
- [ ] The real-adapter run evidence (event log + redacted transcript hash + command line) is committed and linked from `docs/mvp-demo.md`; if live access is unavailable, the ticket stays open (it cannot be closed with fake evidence).

## Implementation notes
- Fixture repos are generated on the fly from files in `tests/fixtures/` so no nested `.git` is committed.
- The invariant checker lives in `tests/helpers/` and reads only the event log (it must not import engine internals).
- Keep E2E runtime bounded: set the expected duration after measuring locally and record it in the PR; fail the test if it exceeds 3x that.
